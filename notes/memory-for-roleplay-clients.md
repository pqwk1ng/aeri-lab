# 长对话记忆：给 AI 角色扮演客户端的三条路线

> 2026-11-26 · aeri 的设计笔记，来自对两个开源客户端的源码深读（见文末来源）

玩 AI 文字游戏/角色扮演，玩到几十上百轮之后最扫兴的事就是 AI「失忆」：忘了开局埋的信物叫什么，忘了某句关键原话。大多数客户端靠**摘要**续命——把早期剧情压成梗概。摘要管大势，但细节必然丢。这两年开源社区摸出了三条互补的路线：

## 路线一：原文召回（FTS5 + BM25）

给**全部历史消息**建全文索引（SQLite FTS5）。每次发送时，拿玩家最新这句话构建查询：分词、去停用词、最多取 8 个词、OR 连接，用 BM25 在**当前会话内**检索不在近期窗口里的旧消息，排除已在上下文窗口内的，最多取 3 条、总量约 300 token，以「早先剧情回想」块注入。

要点：
- 索引前先剥掉模型的思考块（`<think>`），不然检索全是噪音
- 召回必须有硬上限（条数 + token 双限），不然长局必爆上下文
- 检索全程失败静默：召回是锦上添花，绝不能挡住正常发送

## 路线二：结构化记忆槽

在原文之上再维护一层结构化状态：记忆按类型分槽（状态 / 事件 / 置顶 / 历史摘要），每条有生命周期（生效 / 已解决 / 已过期 / 待复核），且**记录来源消息 ID**——任何一条记忆都能追溯到它出自哪句原话，错了能查、能纠。

配套的两件：动态选角表（每个角色的事实单独存）和场景连续性状态（当前地点、时间、进行中的活动、未解决的动作）。AI 写跑偏时，先查这三张表。

## 路线三：按需回查，不背全文

另一种思路（Agent 酒馆类实现）：正文全部完整保存，但不预先塞进上下文；让 Agent 在需要时自己去回查原文，配合上下文压缩。这样几百层对话仍能记起开局细节，代价是多一步工具调用。

同类实现还把生成拆成三步——正文、变量结算、候选项各自由模型完成一遍，状态栏由固定模板按变量渲染，不再让模型自己输出格式，格式翻车率大幅下降。长文档/剧本玩法则按片段读取推进，不整本塞上下文。

## 怎么选

- 纯浏览器、零后端：路线一的等价实现（分词 + BM25 可以纯前端跑），加轻量版路线二
- 有本地数据库（桌面/移动端）：路线一 + 二完整版
- Agent 框架可调工具：路线三上限最高

三条路线不互斥。摘要、召回、结构化状态各管一层，是目前我看到的最稳组合。
